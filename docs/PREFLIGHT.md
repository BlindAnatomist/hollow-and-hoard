# Repository Preflight

Use this checklist before every substantial implementation, repair, recovery, asset transfer, workflow, review, publication, deployment, or owner handoff.

Last reconciled: August 5, 2026.

## 1. Read mandatory authority records

Read before acting:

1. `AGENTS.md`;
2. `.github/ZERO_DOLLAR_AUTOMATION_POLICY.md`;
3. `docs/implementation-status.md`;
4. `docs/PROJECT_DEFINITION.md`;
5. `docs/KNOWN_PROBLEMS_AND_PROVEN_SOLUTIONS.md`;
6. `docs/KNOWN_PROBLEMS_AND_PROVEN_SOLUTIONS_HAH-009.md`;
7. every phase, acceptance, art, test, or repair record named by the assignment.

When the mechanism matches an imported solution, inspect the exact current source record in Val Music Vault or Guitar Eyes before choosing a method.

Do not treat chat memory, PR prose, status prose, branch names, recent activity, screenshots, generated packages, or workflow summaries as authority.

## 2. Establish exact operating context

Record before editing:

- repository: `BlindAnatomist/hollow-and-hoard`;
- active branch;
- immutable starting commit;
- open PR and its actual base and head;
- requested outcome;
- exact files and behavior in scope;
- accepted behavior and assets that must remain unchanged;
- actions explicitly outside scope;
- minimum proof;
- exact stop condition.

Do not write until these are known.

## 3. Prove source authority and lineage

Verify:

1. the current runtime entry points and the implementation they actually load;
2. the exact accepted base;
3. branch ancestry from that base;
4. inherited tests and accepted behavior contracts;
5. built or hosted artifact identity when relevant;
6. the distinction between application-source authority and documentation-only closure commits.

A green test suite proves only the contract it contains. A thinner replacement suite is not preservation evidence.

Repository authority is relational. Compare the candidate with the exact accepted base; do not enforce or assume an invented clean repository shape.

If runtime source, ancestry, tests, and documentation disagree, stop and classify the authority conflict before any write.

Search the local register by:

Relevant cross-repository foundations include:

Begin with the proven route. State the concrete incompatibility before departing from it.

## 5. Bound the execution envelope

Separate:

- source creation or repair;
- asset preparation;
- formatting;
- dependencies;
- focused tests;
- complete tests and build;
- transport;
- hosted proof;
- deployment or publication;
- owner or Cynthia acceptance.

Assign each part to the least expensive capable environment. The size of the source diff does not determine the size of the execution assignment.

Do not use Actions, connectors, Work, or the owner for tasks a cheaper capable route can complete reliably.

## 6. Apply the authority-collapse and recovery-stop gate

Before recovery, record:

- the exact object believed authoritative;
- repository, branch or commit, path, size, hash, and structure;
- runtime landmarks expected after recovery;
- accepted base and ancestry requirements;
- inherited tests that must remain;
- maximum attempt count;
- one materially different fallback;
- reconstruction threshold.

Mandatory stop rules:

1. The first identity or integrity failure stops transfer and triggers diagnosis.
2. One materially different intact-source route may be attempted only when positive evidence supports it.
3. A second contradiction, identity failure, or proof that remaining sources are known-corrupt closes recovery.
4. Once closed, do not continue comment extraction, overlapping fragments, rendered-text copying, Base64 repair, workflow archaeology, byte splicing, trigger experiments, or force-push speculation.
5. Preserve damaged evidence without resuming product work from it.
6. Compare recovery effort and risk with clean reconstruction.
7. Choose reconstruction immediately when it is cheaper, safer, or more verifiable.
8. Stop recovery immediately when the owner directs reconstruction.

Do not let theoretical recoverability override operational value.

## 7. Classify transport before moving bytes

Ask:

1. Does a complete trustworthy object already exist?
2. Is the remaining task only intact transport?
3. Or does development, formatting, testing, conflict resolution, build, or multi-file atomic work remain?

If only transport remains:

- permit no more than two attempts with a truncating or rejecting mechanism;
- prefer an existing verified artifact, direct modular source, authenticated checkout, or bounded intact owner handoff;
- do not use PR comments, overlapping ranges, trigger commits, scheduled workflows, Git trees, or Actions merely to carry bytes;
- verify filename, byte count, hash or blob, source commit, destination branch and path, complete contents or exact diff, and absence of unrelated changes.

If development remains, use a capable environment. Do not disguise development as transport.

## 8. Evaluate one bounded owner action

A handoff is allowed only when:

- the exact target and action are known;
- authorization already exists;
- identity, safety, and acceptance evidence are established;
- assistant tools cannot perform the same exact action or would create a different result;
- the action is deterministic and VoiceOver-manageable;
- the owner need not search, compare, diagnose, edit, choose a branch, resolve conflicts, inspect hashes, or make architecture decisions;
- no cost, secret, private media, merge, deployment, publication, or destructive ambiguity is involved.

Prepare:

- exact address;
- exact accessible control;
- expected confirmation;
- prohibited alternatives;
- exact filename or commit message when applicable;
- precise stop condition;
- independent post-action verification.

Do not replace one precise owner action with extended automation improvisation.

## 9. Protect public, licensing, and zero-dollar boundaries

Verify before adding a file, asset, workflow, service, or deployment:

- no secret, credential, private record, private correspondence, or unauthorized media is exposed;
- licensing permits public use;
- no paid runner, API, storage, subscription, trial conversion, or overage is introduced;
- deployment, publication, merge, and external mutation have separate authorization;
- the operation cannot retrigger itself or alter unrelated state.

When cost or licensing status is uncertain, stop.

## 10. Preserve Cynthia-first product authority

For game changes, define how the checkpoint will evaluate:

- professional visual quality;
- touch movement and drag satisfaction;
- sound comfort and audibility;
- story comprehension;
- board calmness and environmental life;
- pacing, delight, and desire to continue.

Automated checks establish contracts. Cynthia establishes the intended player experience.

Keep story and how-to-play material separate from the active board when that preserves visual space.

## 11. Format to a fixed point when declared

When the repository declares a pinned formatter:

1. install from the exact lockfile when necessary;
2. run the formatter;
3. inspect or hash the working-tree diff;
4. repeat until two successive diff hashes match, with a maximum of four passes;
5. stop and isolate the exact file or construct if convergence fails;
6. inspect the stable diff for semantic change;
7. run the formatter check;
8. only then run the broader gate;
9. commit source and canonical formatting together.

Required sequence:

`format to a fixed point, inspect, then check`

Do not invent a formatter command when the repository does not declare one. Do not spend an acceptance run discovering ordinary formatting debt.

## 12. Define diagnostic verification before hosted execution

Record the minimum required evidence, such as:

- source authority and ancestry;
- explicit changed-file boundary;
- syntax, type, or rule checks;
- focused state-machine or gameplay tests;
- inherited regression tests;
- asset dimensions, bytes, and hashes;
- browser interaction smoke tests;
- mobile and desktop screenshots;
- console and page-error checks;
- production build and asset-boundary inspection;
- hosted exact-file read-back;
- Cynthia device acceptance.

Preflight assertions must be named and diagnostic. Report expected and actual values. A failed authority guard is not evidence that tests or builds failed when they never ran.

## 13. Apply the hosted-run circuit breaker

Before the first run:

- complete every available check outside Actions;
- batch all known repairs;
- record exact source commit, commands, expected evidence, and stop condition;
- confirm least privilege, timeout, concurrency, and no unauthorized external mutation.

After the first failed run:

1. stop workflow activity;
2. inspect the complete failed job and logs;
3. classify only the executed failure;
4. preserve successful evidence;
5. search all governing local and cross-repository records;
6. audit the complete affected boundary and batch corrections outside Actions;
7. allow at most one corrective acceptance run.

If the corrective run finds another defect of any kind, the circuit is open. Do not create, edit, trigger, schedule, replace, or rerun another workflow on that branch unless the work moves to a capable unmetered environment or the owner explicitly authorizes one identified, materially different exception after being told the circuit is open.

Rerun only the failed job when possible. Do not repeat successful setup, browser installation, tests, build, packaging, or publication evidence.

## 14. Require failure-preserving materialization

When an authorized process creates lasting source, fixtures, manifests, canonical exports, or evidence:

1. verify immutable authority and structure before dependency installation;
2. run dependency-free transformation and structural checks first;
3. keep documentation mutation outside the application transformation;
4. commit valid lasting work before later broad tests when technically possible;
5. remove temporary automation without deleting lasting work;
6. run focused proof before complete proof;
7. preserve the lasting commit after a later failure;
8. repair forward directly;
9. never regenerate valid material merely to repair a later test, formatter, build, documentation, or publication defect;
10. reconcile records only after proof.

Acceptance must fail forward.

## 15. Preserve trigger and state distinctions

Do not confuse:

- commit creation;
- branch-ref movement;
- PR refresh;
- workflow eligibility;
- queue entry;
- job start;
- artifact creation;
- deploy ingestion;
- build completion;
- publication.

Require positive failure evidence or an exceeded bounded wait before issuing another trigger.

Do not toggle PR state, retarget bases, create marker commits, install workflows on unrelated branches, schedule recurring jobs, or force-push branches as exploratory probes.

## 16. Change methods decisively

After two failures with the same mechanism:

1. stop it;
2. preserve completed evidence;
3. identify the one remaining gate;
4. state why the method is invalid;
5. select a materially different proven route;
6. define its stop condition;
7. report the change before the next consequential action.

Changing names, branches, event types, endpoints, wrappers, or storage locations around the same damaged source is not a materially different route.

## 17. Maintain owner visibility

During multi-step work, report:

- what is complete;
- active gate;
- blocker;
- whether the method remains viable;
- next consequential action.

After two or three tool calls without forward progress, report the lack of progress. Report immediately when a method becomes invalid.

A stream interruption does not mean work continued invisibly.

## 18. Close with exact evidence

Before declaring completion:

- confirm final branch and commit;
- inspect every changed file;
- record checks and results;
- identify Actions runs and deployments;
- identify dependencies, services, assets, or costs introduced;
- verify no unrelated branch, PR, workflow, merge, publication, or external state changed;
- state what remains unverified;
- identify the next bounded step;
- state whether owner or Cynthia action is required.
