# Known Problems and Proven Solutions

Repository: `BlindAnatomist/hollow-and-hoard`

Status: active operational memory

## Purpose

This is the first document to inspect before diagnosing, repairing, transporting, testing, automating, or deploying work in this repository.

It exists to prevent repeated mistakes, preserve failed approaches as warnings, record solutions supported by evidence, and import proven mechanisms from the owner's other repositories without importing their project-specific code or history.

Do not treat chat memory, a PR description, or apparent tool activity as authoritative when repository evidence is available.

A technically plausible method can still be operationally defective when it wastes owner time, GitHub Actions, repository clarity, or project momentum.

## Required use

Before consequential work:

1. Read `AGENTS.md` and `docs/PREFLIGHT.md`.
2. Search this file by symptom, mechanism, failed approach, service, and file type.
3. Inspect linked repository evidence.
4. Start from the proven method when the same mechanism applies.
5. State why a new method is required before departing from an existing solution.
6. Record new failures and confirmed solutions before closing the assignment.

## Entry states

- `local-proven`: established by Hollow & Hoard repository or player evidence.
- `cross-repository-proven`: deliberately imported from another owner repository and accepted as governing here.
- `candidate`: plausible and authorized for bounded proof, but not yet accepted in Hollow & Hoard.
- `failed-do-not-repeat`: attempted and shown to be inadequate, harmful, or wasteful.
- `superseded`: retained for history but replaced by a better solution.

## HAH-001 — Proven operational memory was ignored and a known problem was treated as novel

State: `failed-do-not-repeat`

First observed: 2026-08-02

Affected area: Version 2 source and art transport

### Symptoms

The Version 2 design, source package, and improved art were already substantially prepared. The remaining obstacle belonged to file transport and repository integration.

Instead of first inspecting Val Music Vault's `AGENTS.md` and known-problems records, especially VMV-009 and VMV-011 through VMV-016, the assistant treated the obstacle as a new research problem. More than an hour was spent generating increasingly elaborate routes while the owner repeatedly encountered stalled or interrupted streams.

### Cause

- Cross-repository operational memory was not reconstructed before choosing a method.
- The existing Hollow & Hoard instructions expressed general principles but did not force inspection of proven source records.
- Reasoning expanded sideways into new mechanisms instead of converging on the established solution class.
- The assistant continued optimizing method design after the owner had already identified that Music Vault contained the answer.

### Failed-do-not-repeat approaches

- Treat a recurring GitHub or connector problem as novel without searching the owner's proven repositories.
- Rely on remembered summaries when the governing files are available.
- Use technical ingenuity as a substitute for procedural reconstruction.
- Continue experimenting after the owner identifies a known source of proven solutions.

### Required solution

1. Search the local HAH register first.
2. When the mechanism matches a cited VMV record, inspect the exact current Music Vault source before acting.
3. Copy the governing mechanism into Hollow & Hoard's own instructions so future sessions are self-contained.
4. Begin with the proven route.
5. When departing from it, state the concrete incompatibility and obtain a new bounded stop condition.

### Evidence

- The prolonged Version 2 transport session on 2026-08-02.
- Val Music Vault Phase 10 `AGENTS.md` and VMV-009, VMV-011, VMV-012, VMV-013, VMV-014, VMV-015, and VMV-016.
- This governance rewrite on branch `governance-import-vmv-lessons`.

### Prevention rule

Known operational memory is executable project infrastructure. Read it before inventing a method.

## HAH-002 — Connector truncation became fragment reconstruction instead of intact transport

State: `failed-do-not-repeat`

First observed: 2026-08-02

Affected area: Version 2 source archive and production art atlas

Cross-repository foundations: VMV-009 and VMV-016

### Symptoms

The assistant had a complete verified Version 2 package and a prepared production atlas. Connector and message-size boundaries prevented carrying the largest files through one ordinary GitHub contents call.

Work then expanded into:

- Base64 segmentation;
- PR-comment chunk relays;
- attempts to repair a missing character inside one chunk;
- Git blob and tree experiments;
- temporary import workflows;
- scheduled workflows;
- marker commits;
- workflow placement on multiple branches;
- PR closing, reopening, and base changes;
- repeated attempts to infer whether a force-push or import had occurred.

The remaining problem was transport, but it was repeatedly treated as development and workflow architecture.

### Cause

- Obtaining or moving intact bytes was conflated with creating, repairing, testing, and accepting the files.
- The connector's size boundary was treated as a puzzle to defeat rather than a method constraint.
- Exactness became loyalty to fragment reconstruction instead of preservation of the intact object.
- GitHub Actions was recruited as a byte-transfer service.

### Failed-do-not-repeat approaches

- Continue overlapping or segmented transfer after the connector has proved it cannot carry the artifact intact.
- Use PR comments as an artifact store.
- Repair truncated Base64 by searching for missing characters when an intact source exists.
- Create trigger commits, recurring workflows, or branch rewrites merely to reconstruct an already complete file.
- Convert one failed transport into a multi-service deployment architecture.
- Claim progress because more fragments or workflows exist when the repository still lacks the complete file.

### Required solution

1. Allow no more than two attempts with the same truncating mechanism.
2. Stop and classify the remaining problem as transport or development.
3. If the complete trustworthy object exists, use one of these routes in order:
   - an existing verified artifact;
   - a connector or API capable of accepting the complete file reference;
   - an authenticated checkout capable of committing the intact file;
   - a bounded owner-operated complete-file download, attachment, or upload;
   - a capable execution environment only when transformation or multi-file atomic work remains.
4. Do not use Actions merely to move intact bytes.
5. Verify file name, byte count, dimensions or structure, hash or blob identity, destination branch and path, and absence of unrelated changes.

### Acceptance boundary

The prohibition on fragment reconstruction is locally established by failure.

The owner-operated intact-file route remains `candidate` for Hollow & Hoard until a harmless deterministic round trip is completed and verified. It must nevertheless be evaluated before any future fragment relay.

### Prevention rule

When the bytes already exist intact, move the intact object. Do not rebuild it from the shadow cast by a connector limit.

## HAH-003 — GitHub Actions became a transport, trigger, and debugging loop

State: `failed-do-not-repeat`

First observed: 2026-08-02

Affected area: Version 2 import and browser-gate preparation

Cross-repository foundation: VMV-011

### Symptoms

Temporary workflows were created or modified to import files, expose trigger behavior, reconstruct packages, schedule browser gates, publish evidence, and move branch refs. Workflow event types and locations changed repeatedly. PR state and base branch were altered in attempts to make workflows visible or eligible.

Actions was no longer an acceptance checkpoint. It had become the environment in which the method itself was being discovered.

### Cause

- The workflow circuit breaker was absent from Hollow & Hoard's effective instructions.
- Push, pull-request, schedule, and manual-dispatch eligibility were diagnosed experimentally instead of from one bounded model.
- No hard limit separated one corrective run from a new debugging loop.
- Free public-repository minutes were treated as removing the operational cost.

### Failed-do-not-repeat approaches

- Create a new workflow after each trigger or transport uncertainty.
- Change event types or workflow branches as iterative probes.
- Use a recurring schedule as a fallback for an operation that should occur once.
- Repeat browser installation or earlier successful checks because a later packaging or transport step failed.
- Preserve temporary workflows after their bounded purpose ends.
- Interpret broad owner authorization to finish as permission for unlimited runs.

### Required solution

Before the first run:

1. Complete every available source, syntax, rule, asset-integrity, formatting, and packaging check outside Actions.
2. Record exact source authority, commands, expected evidence, and stop condition.
3. Use one bounded workflow with least privilege, timeout, concurrency control, and no unauthorized external mutation.

After the first failed run:

1. Stop workflow activity.
2. Inspect the complete failed job and logs.
3. Preserve successful evidence.
4. Diagnose and batch all known repairs outside Actions.
5. Permit at most one corrective acceptance run.

If that corrective run reveals another defect, the circuit is open. Do not create, edit, trigger, schedule, replace, or rerun another workflow on the branch without telling the owner and receiving explicit authorization for one identified additional run.

### Prevention rule

Acceptance automation verifies a prepared result. It must never become the place where the result or transport method is invented one failure at a time.

## HAH-004 — Branch, PR, workflow, and deployment metadata were treated as one state

State: `failed-do-not-repeat`

First observed: 2026-08-02

Affected area: PR 2 and Version 2 branch verification

Cross-repository foundation: VMV-012

### Symptoms

The assistant repeatedly inferred success or failure from stale or partial metadata:

- a PR description claimed Version 2 behavior while the branch still served the Version 1 controller;
- a force-push or workflow was inferred from branch or PR snapshots that had not refreshed;
- the absence of a visible run through one connector endpoint was treated as proof that no run existed;
- PR state and base branch were changed to provoke events;
- new marker commits were created before positive failure evidence existed.

### Cause

Different state transitions were collapsed:

1. commit creation;
2. branch-ref movement;
3. PR snapshot refresh;
4. workflow-event eligibility;
5. queue entry;
6. job start;
7. artifact creation;
8. deployment ingestion;
9. build completion;
10. publication.

### Failed-do-not-repeat approaches

- Treat a PR body as proof of implemented code.
- Treat stale PR metadata as authoritative branch state.
- Treat one connector's inability to list a push or scheduled run as proof that the run did not occur.
- Issue another trigger after only an immediate unchanged read-back.
- Toggle PR state or change its base to probe event behavior.
- Force-push or create marker commits without a bounded diagnosis.

### Required solution

- Verify code by fetching the exact branch file or commit.
- Verify branch movement through the exact ref or immutable commit.
- Verify workflows through the run and failed-job evidence supported by the available endpoint.
- Verify hosted work through the exact artifact or deploy identity.
- Define a bounded wait window before classifying latency as failure.
- Require positive failure evidence before issuing a second trigger.
- When a connector cannot observe the relevant event type, state that observability limit rather than inventing success or failure.

### Prevention rule

A plan, PR description, trigger, run, artifact, deploy, and published application are different objects. Verify the object that carries the claim.

## HAH-005 — A bounded owner action was deferred in favor of prolonged autonomy

State: `cross-repository-proven`

Imported: 2026-08-02

Affected area: dashboards and complete-file transport

Cross-repository foundations: VMV-015 and VMV-016

### Problem

The owner can perform a narrow deterministic download, attachment, upload, or button activation with VoiceOver. The assistant should protect the owner from exploratory dashboard crawling, but that protection must not become refusal to use one exact safe action when assistant tools cannot perform it.

### Failed-do-not-repeat approaches

- Spend extended time inventing indirect transports after the exact remaining action is known.
- Use a connector action that creates a materially different result merely to preserve assistant autonomy.
- Ask the owner to use a CLI when the operation is only pressing one button or transferring one known file.
- Conversely, send the owner into GitHub or another dashboard without an exact address, exact control, prohibited alternatives, and stop condition.

### Governing solution

A bounded owner handoff is permitted only when:

1. the action is already authorized;
2. the exact target and state are verified;
3. assistant tools cannot perform the same action reliably;
4. the action is narrow and VoiceOver-manageable;
5. the owner need not search, compare, diagnose, edit, choose a branch, or interpret unfamiliar options;
6. no cost, secret, private media, merge, deployment, or broader mutation is hidden inside the handoff.

The assistant provides:

- exact address;
- exact control name;
- expected confirmation;
- nearby controls not to use;
- exact file name or commit message when applicable;
- stop condition.

The assistant then performs independent read-back and integrity verification.

### Hollow & Hoard boundary

The general dashboard-action mechanism is cross-repository proven through VMV-015.

The complete-file iPhone round trip remains a candidate under VMV-016 until its harmless documentation test is accepted. It must still be considered before fragment reconstruction or Actions-based byte transport.

### Prevention rule

Precision is better than autonomy theater. Protect the owner from exploration, not from one exact safe action that decisively closes the gate.

## HAH-006 — Story explanation crowded the wrong surface and the Hoard meaning was not communicated

State: `local-proven problem; solution candidate`

First observed: 2026-08-02

Affected area: Cynthia's Version 1 play test

Cross-repository foundation: VMV-013

### Symptoms

Cynthia liked the game's appearance and controls but did not understand whether there was a story or what the Hoard represented. The active board also felt plainer and less alive than the concept art suggested.

Adding more explanation directly around the board would reduce visual space and risk turning play controls, state, story, and instructions into one crowded surface.

### Cause

The game contained an internal premise—completed lineages become relics and the Hoard is what the Hollow remembers—but did not introduce that premise before play. Explanatory content and action space had not been assigned separate surfaces.

### Failed-do-not-repeat approaches

- Attach paragraphs of story or instructions to board controls.
- Crowd the active game screen with repeated lore and how-to-play prose.
- Use control labels to carry narrative explanation.
- Assume the phrase `Hoard Chamber` explains its meaning.
- Add more decorative content without clarifying the player's purpose.

### Authorized candidate solution

- Create a dedicated introductory screen with the game title, concise premise, minimal how-to-play guidance, and one `Start Game` action.
- Explain that creatures grow through lineages, completed lineages leave relics, and the Hoard is what the Hollow remembers.
- Keep the active board visually calm.
- Use the Codex for creature knowledge and the Hoard screen for relic meaning and persistent memory.
- Keep control names concise, status feedback separate, and story subordinate to play once the game begins.

### Acceptance boundary

Cynthia has authorized the direction but has not yet tested the implemented introductory screen. Do not mark the solution locally proven until she confirms that the story and Hoard are understandable without making play feel crowded.

### Prevention rule

Controls name actions. Status reports events. Story belongs to a story surface. The board should remain a place to play.

## HAH-007 — Acceptance must not be the first formatter pass

State: `cross-repository-proven`

Imported: 2026-08-02

Affected area: any future repository using a pinned formatter

Cross-repository foundation: VMV-014

### Problem

Connector or API edits may produce formatting debt. One formatter write pass may also change again on a second pass. Spending an acceptance run to discover either condition wastes the rest of the gate.

### Failed-do-not-repeat approaches

- Treat a successful browser or deployment build as formatting evidence.
- Manually rewrap large source and documentation files by eye.
- Weaken formatting coverage to make CI pass.
- Assume one write pass reached a fixed point.
- rerun the complete acceptance gate after every formatting pass.

### Governing solution

When Hollow & Hoard has a repository-pinned formatter:

1. install from the exact lockfile when needed;
2. run the formatter;
3. inspect or hash the diff;
4. repeat until two successive diff hashes match, with a maximum of four passes;
5. stop and isolate the file if convergence fails;
6. run the formatter check;
7. inspect the stable diff for semantic changes;
8. run the complete check suite;
9. commit source and canonical formatting together.

Required sequence:

`format to a fixed point, inspect, then check`

Do not invent a formatter when the repository does not have one.

### Prevention rule

Formatting is preparation for acceptance, not a discovery made by acceptance.

## HAH-008 — A stream interruption was allowed to obscure whether work had stopped

State: `failed-do-not-repeat`

First observed: 2026-08-02

Affected area: owner visibility and session control

### Symptoms

The interface repeatedly displayed `streaming interrupted`, `stopped analyzing`, or an invitation to retry. The owner left and returned to the thread without knowing whether work remained active. At several points no work was continuing, but the visible state did not make that clear.

### Cause

Tool activity, message streaming, and actual execution were not distinguished clearly enough. Progress reports came too late, and the assistant sometimes described intended continuation more strongly than the actual execution state supported.

### Failed-do-not-repeat approaches

- Imply that work continues invisibly after the stream or analysis has stopped.
- Leave the owner to infer state from the app's retry message.
- Report plans instead of the exact completed repository state.
- Continue multiple tool calls without a concise gate update.

### Required solution

- State plainly whether a repository write or external operation actually completed.
- After interruption, reconstruct exact state before continuing.
- Report branch, commit, completed files, and remaining gate when available.
- During long operations, update after two or three tool calls or immediately when the method fails.
- Never promise asynchronous continuation. If execution stopped, say it stopped.

### Prevention rule

The owner should never have to guess whether the assistant is working, stalled, or finished.

## Repository-wide product standards

### Completion must create space, not punish success

Completed lineages move relics into the Hoard so success frees active board space and changes the world.

### Preserve approved art identity

When an approved design is good, refine, extract, upscale, clean, or locally repair it. Do not regenerate the visual identity from scratch merely because an individual asset needs correction.

### Production art requires direct inspection

A green test can prove dimensions, decoding, cropping, and runtime rendering. It cannot prove beauty, sharpness, contamination, professional quality, or visual coherence. Directly inspect the actual screenshots and assets, then translate that judgment for the owner.

### Cynthia acceptance is irreducible

Automation cannot establish whether movement feels satisfying, sound is comfortably audible, characters look professional, the story is understood, or the game creates delight. Preserve a stable exact build for Cynthia's judgment.
